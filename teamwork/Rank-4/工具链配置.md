# 工具链配置 v1.0（WorkBuddy + Godot MCP）

> 结论先行：M0 的第一件事不是出图，是**真跑通「WorkBuddy → Godot MCP → Godot 编辑器」这条链**。本文给完整 `mcp.json`、Godot 4 PATH、专家分工、使用边界、M0 连通性验证步骤与小版本兼容性清单。**不写任何探针 / 测量 / preflight 脚本**，所有验证都是人工操作或真跑一次 MCP 调用。

## 1. `mcp.json` 完整配置

配置文件路径：`C:\Users\<用户名>\.workbuddy\mcp.json`（注意：**不是** `.mcp.json`，无点前缀）。已存在其它 server 时只**合并 `mcpServers` 下的 `godot` 条目**，不要覆盖整个文件。

### 1.1 Windows 主配置（本项目 OS 为 win32，推荐）

```json
{
  "mcpServers": {
    "godot": {
      "command": "cmd",
      "args": ["/c", "npx", "-y", "@coding-solo/godot-mcp"],
      "env": {
        "DEBUG": "true"
      },
      "disabled": false
    }
  }
}
```

### 1.2 跨平台 / 最简配置（与总纲 §1 一致）

```json
{
  "mcpServers": {
    "godot": {
      "command": "npx",
      "args": ["@coding-solo/godot-mcp"],
      "env": { "DEBUG": "true" },
      "disabled": false
    }
  }
}
```

### 1.3 字段说明与可选变体

| 字段 | 说明 |
|---|---|
| `command` / `args` | Windows 下 `npx` 常需经 `cmd /c` 启动，否则 spawn 可能失败；`-y` 免交互确认，避免非交互环境卡住 |
| `env.DEBUG` | 打开后 MCP 输出详细日志，M0 排障时保留；稳定后可设 `"false"` |
| `disabled` | 必须为 `false` |
| 可选 `env.GODOT_PATH` | 部分版本支持用环境变量指定 Godot 可执行文件路径（如 `"C:\\Program Files\\Godot\\Godot_v4.3-stable_win64.exe"`，JSON 中反斜杠需转义）。**该变量名以本地 `@coding-solo/godot-mcp` 实际版本为准**；优先依赖系统 PATH，不识别时删掉这一项 |

> 配置写入后**不会自动生效**：需在 WorkBuddy 连接器管理页右上角的自定义连接器入口，对新出现的 `godot` 条目点「信任 / 启用」。启用后用 `tools/list` 真跑确认工具清单（§5）。
> 本项目**零外部依赖**：除 `@coding-solo/godot-mcp` 外不配置任何云服务、素材服务或需付费的 server。

## 2. Godot 4 PATH 配置

| 项 | 要求 |
|---|---|
| 版本 | **Godot 4 标准版（GDScript，非 .NET / Mono 版）**；建议 4.3 / 4.4 稳定版，最低 4.2 |
| 可执行文件 | 例如 `C:\Program Files\Godot\Godot_v4.3-stable_win64.exe`，重命名为 `godot.exe` 便于调用 |
| PATH | 把可执行文件所在目录加入系统 `PATH`；Windows 用「系统属性 → 环境变量 → 系统变量 Path → 新建」，或用 PowerShell 临时设置 |
| 验证（真跑） | 新开一个终端执行 `godot --version`，应输出 `4.x.x.stable...`；输出带 `mono` 即为错误版本 |
| 工程根 | `F:\Game\aierdengfahuan\`（约定，尚未建立）；`project.godot` 由 1 号创建，4 号不碰 |
| 编辑器状态 | MCP 操作场景树需要 **Godot 编辑器已启动并打开该工程**，且工程内装好 MCP 配套插件（若该版本要求） |

```bash
godot --version
godot --headless --path "F:/Game/aierdengfahuan" --quit
```

> 第二条用于确认工程可被无头模式加载（1 号建好 `project.godot` 后才有意义）。两条都是人工执行的一次性命令，不是脚本、不是探针。

## 3. 专家角色分工表（WorkBuddy 内置预设）

| 角色 | 负责 | 喂给它的长期约束 | 明确不交给它 |
|---|---|---|---|
| **节点通**（Godot 脚本工程师） | 场景树搭建、`GDScript` 编写、节点属性修改、MCP 驱动 Godot 操作、逻辑校验与重构 | 项目说明书：`00-项目总纲.md`、`00-协作契约.md`、I-1~I-6 接口表、命名规范 | 不让它决定视觉色号、帧数节奏、Boss 手感 |
| **游戏逻辑** | 状态机、数值冲突排查、数据表一致性检查、信号连线核对 | 战斗数据表结构、flag 三段式命名、`SaveDelta` 口径（3 号定义） | 不让它改接口签名、不让它动存档文件 |
| **游戏美术师**（本工位视角） | 风格锚点、色板、提示词包、资产规格、一致性评审、AI 底稿标注 | `HD-2D视觉规范.md`、`prompt_skeleton.json`、`资产交付契约.md` | 不写引擎代码 / shader、不做数值设计、不做商店页素材 |

**切换原则**：一次任务只挂一个主角色，把对应的长期约束文档喂进去；跨角色结论以**文档**交接，不靠对话记忆。WorkBuddy 不会私自改接口、改变量，但也不会替人做审美与手感判断。

## 4. WorkBuddy「能做 / 不要让它做」边界表

### 4.1 让它做

| 类别 | 具体事项 |
|---|---|
| 工程操作 | 通过 Godot MCP 创建 / 修改 / 删除节点、读写节点属性、保存场景、读取场景树 |
| 代码 | 编写 `GDScript`、搭建状态机骨架、重构、按契约补信号连接 |
| 校验 | 全局排查逻辑漏洞、数值冲突、时序 bug、接口签名一致性、命名规范符合性 |
| 结构化产出 | 数据表骨架、Resource 定义、`import.json` / manifest 字段核对、批量文本替换 |
| 长上下文 | 一次吃透整套工程脚本做跨文件一致性检查（本地读写，不烧 token） |

### 4.2 不要让它做

| 类别 | 原因 | 由谁兜底 |
|---|---|---|
| 像素美术的**最终审美决策** | 它发现不了拼凑感、明度层级塌陷、剪影糊 | 人工 + 本工位视觉规范 §8 验收清单 |
| Boss 招式的**手感**调校 | 无敌帧、前摇后摇、削韧节奏必须上手玩 | 2 号 + 人工试玩 |
| 关卡**密度**的设计判断 | 「这个区域太空」是体验判断，不是逻辑判断 | 主 AI / 人工试玩（总纲 §5 风险 2） |
| 私自改接口 / 变量 / 契约 | I-1~I-6 已锁定 | 主 AI 裁决 |
| 决定色号、帧数节奏、构图 | 属美术冻结项 | 4 号规范 + 人工 |
| 生成最终商用级美术成品 | AI 出的是底稿 | Aseprite 人工精修 |
| 引入付费 / 云服务 / 外部素材服务 | 违反零付费零外部依赖决策 | 一律禁止 |

> 铁律：**每个里程碑必须自己上手玩**。WorkBuddy 能校验逻辑和数值，但发现不了「这个 Boss 不公平」「这个区域太空」。

## 5. M0 连通性验证步骤（真跑：创建节点 → 修改属性 → 读回确认）

> 全程人工操作 + MCP 工具调用，**不写脚本、不建探针目录、不产出 `.gd`/`.tscn` 测量文件**。下表工具名为**语义名**，实际名称以 `tools/list` 真跑返回为准（不同 `@coding-solo/godot-mcp` 版本命名有差异，这是 §6 兼容性检查的第一项）。

| 步 | 操作 | 预期结果 | 不通过处理 |
|---|---|---|---|
| 0 | 终端执行 `godot --version` | 输出 `4.x.x.stable`，无 `mono` | 重装标准版 / 修 PATH |
| 1 | 启动 Godot 编辑器，打开 `F:\Game\aierdengfahuan` 工程 | 编辑器正常加载，无导入报错 | 由 1 号修 `project.godot` |
| 2 | WorkBuddy 连接器页对 `godot` 点「信任 / 启用」 | 状态变为已连接 | 检查 `mcp.json` 的 `command`/`args`；Windows 改 `cmd /c` |
| 3 | 发起 `tools/list`，记录实际返回的工具名清单 | 至少包含「读场景树 / 建节点 / 改属性 / 读属性 / 保存场景」五类能力 | 记下实际名，后续步骤按真名调用；写进 M0 交付记录 |
| 4 | 调用「读场景树」 | 返回当前打开场景的根节点结构 | 确认编辑器已打开场景（不是空工程） |
| 5 | **创建节点**：在根节点下建一个 `Node2D`，命名 `M0ConnectivityNode` | 返回新节点路径，场景树中可见 | 检查 MCP 插件是否需要在工程内启用 |
| 6 | **修改属性**：把该节点 `position` 设为 `(120, 80)`，`visible` 设为 `true` | 两次调用均返回成功 | 确认属性名在该 Godot 小版本下未变更（§6） |
| 7 | **读回确认**：读取该节点属性 | `position == (120, 80)`、`visible == true` | 若读不回，检查 MCP 是否连到另一个工程实例 |
| 8 | 保存场景 → 关闭并重启编辑器 → 再读一次 | 节点与属性值仍在（持久化正常） | 检查保存路径与 `.tscn` 写入权限 |
| 9 | 删除 `M0ConnectivityNode`，恢复干净场景 | 场景树无残留验证节点 | — |
| 10 | 记录并回报 | 实际 Godot 版本 / MCP 包版本 / `tools/list` 工具名清单 / 第 6~7 步读回值 | 交主 AI 汇总 M0 |

**通过标准**：第 5→6→7 步闭环成立（建得出、改得动、读得回），且第 8 步持久化成立。这条链没通之前不进入 ComfyUI 出图，避免把「工具链问题」误判成「美术问题」。

> 第 5~9 步的临时节点是**一次性的连通性验证动作**，不是探针脚本、不落盘任何 `.gd` 文件；验证完即删除。
